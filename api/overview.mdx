The EHR REST API gives you programmatic access to every resource on the platform — patients, appointments, encounters, prescriptions, orders, and billing claims. Every request travels over HTTPS, returns JSON, and follows predictable RESTful conventions so you can start integrating quickly and build with confidence.

## Base URL

All API requests target the following base URL. Append the endpoint path to this root — for example, `https://api.example-ehr.com/v1/patients`.

```
https://api.example-ehr.com/v1
```

<Note>
  All traffic must use **HTTPS**. Plain HTTP requests are rejected with a `400
  Bad Request` response.
</Note>

## Authentication

The API uses **Bearer token authentication**. Include your API key in the `Authorization` header of every request.

```
Authorization: Bearer YOUR_API_KEY
```

You can generate and manage API keys from **Settings → API Keys** in your dashboard. See the [Authentication guide](/api/authentication) for full details, including the OAuth-style token exchange endpoint.

## Making a Request

Here is a minimal authenticated request that retrieves a list of patients:

```bash
curl -X GET https://api.example-ehr.com/v1/patients \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json"
```

## Content Type

Send all request bodies as JSON and set the `Content-Type` header to `application/json`. The API always returns JSON responses.

```
Content-Type: application/json
```

## Rate Limiting

Each API key is limited to **1,000 requests per minute**. The response headers on every request report your current usage:

| Header                  | Description                                              |
| ----------------------- | -------------------------------------------------------- |
| `X-RateLimit-Limit`     | Maximum requests allowed per minute for your API key     |
| `X-RateLimit-Remaining` | Requests remaining in the current one-minute window      |
| `X-RateLimit-Reset`     | Unix timestamp (UTC) when the current window resets      |

When you exceed the limit, the API returns a `429 Too Many Requests` response. Wait until the window resets before retrying, or implement exponential back-off in your client.

<Tip>
  If your integration regularly approaches the rate limit, batch read operations
  using the `limit` query parameter and use cursor-based pagination instead of
  issuing many individual requests.
</Tip>

## Pagination

List endpoints return paginated results using **cursor-based pagination**. Use the `limit` and `cursor` query parameters to page through large result sets.

| Parameter | Type    | Description                                                                    |
| --------- | ------- | ------------------------------------------------------------------------------ |
| `limit`   | integer | Number of records to return per page. Defaults to `20`; maximum is `100`.      |
| `cursor`  | string  | Opaque cursor returned in the previous response. Omit to start from the first page. |

The response envelope includes a `next_cursor` field. When `next_cursor` is `null`, you have reached the last page.

```json
{
  "data": [ /* ... records ... */ ],
  "next_cursor": "eyJpZCI6IjEyMyJ9",
  "total": 340
}
```

Pass `next_cursor` as the `cursor` parameter in your next request:

```bash
curl -X GET "https://api.example-ehr.com/v1/patients?limit=50&cursor=eyJpZCI6IjEyMyJ9" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json"
```

## Versioning

The current stable API version is **v1**, reflected in the base URL path. When breaking changes are introduced, a new version path (e.g., `/v2`) is released and the previous version is supported for a minimum of 12 months. Non-breaking additions — new optional fields, new endpoints — may be added to the current version at any time.

<Note>
  Pin your integration to the explicit version path (`/v1`) to avoid unexpected
  behavior if the un-versioned root URL ever resolves to a newer version.
</Note>

## Error Response Format

All errors follow a consistent JSON structure:

```json
{
  "error": {
    "code": "validation_error",
    "message": "The field 'date_of_birth' must be a valid ISO 8601 date.",
    "details": [
      {
        "field": "date_of_birth",
        "issue": "invalid_format"
      }
    ]
  }
}
```

### HTTP Status Codes

| Status Code | Name                    | When it occurs                                                                 |
| ----------- | ----------------------- | ------------------------------------------------------------------------------ |
| `200`       | OK                      | The request succeeded. Returned for successful `GET` and `PUT` requests.       |
| `201`       | Created                 | A new resource was created. Returned for successful `POST` requests.           |
| `400`       | Bad Request             | The request is malformed or missing required fields.                           |
| `401`       | Unauthorized            | The `Authorization` header is missing, invalid, or the token has expired.      |
| `403`       | Forbidden               | Your API key does not have permission to access the requested resource.         |
| `404`       | Not Found               | The requested resource does not exist.                                         |
| `422`       | Unprocessable Entity    | The request is well-formed but contains semantic validation errors.             |
| `429`       | Too Many Requests       | Your API key has exceeded the rate limit. Retry after the reset window.        |
| `500`       | Internal Server Error   | An unexpected error occurred on the server. Contact support if this persists.  |

## Available Endpoints

The table below summarises every endpoint exposed by the EHR REST API. Detailed request/response documentation is linked from each section.

| Method   | Path                           | Description                                                        |
| -------- | ------------------------------ | ------------------------------------------------------------------ |
| `POST`   | `/auth/token`                  | Exchange credentials for a short-lived access token.               |
| `GET`    | `/patients`                    | List and search patient records.                                   |
| `POST`   | `/patients`                    | Register a new patient.                                            |
| `GET`    | `/patients/{id}`               | Retrieve a single patient by ID.                                   |
| `PUT`    | `/patients/{id}`               | Update a patient's demographic or insurance information.           |
| `GET`    | `/appointments`                | List appointments with optional filters.                           |
| `POST`   | `/appointments`                | Schedule a new appointment.                                        |
| `GET`    | `/appointments/{id}`           | Retrieve a single appointment by ID.                               |
| `PUT`    | `/appointments/{id}`           | Reschedule, update status, or amend appointment details.           |
| `DELETE` | `/appointments/{id}`           | Cancel an appointment.                                             |
| `GET`    | `/clinical/encounters`         | List encounters for a patient.                                     |
| `POST`   | `/clinical/encounters`         | Create a new clinical encounter with SOAP notes and diagnoses.     |
| `GET`    | `/clinical/encounters/{id}`    | Retrieve a single encounter by ID.                                 |
| `POST`   | `/prescriptions`               | Issue an e-prescription to a pharmacy.                             |
| `GET`    | `/prescriptions/{id}`          | Retrieve a prescription and its transmission status.               |
| `POST`   | `/orders/lab`                  | Submit a laboratory order to a connected diagnostic lab.           |
| `POST`   | `/orders/imaging`              | Submit a diagnostic imaging order to a radiology provider.         |
| `GET`    | `/billing/claims`              | List billing claims with optional filters.                         |
| `POST`   | `/billing/claims`              | Submit a new billing claim.                                        |
| `GET`    | `/billing/claims/{id}`         | Retrieve a single billing claim and its adjudication status.       |
| `GET`    | `/users`                       | List user accounts in your organization.                           |
| `POST`   | `/users`                       | Create a new user account and assign a role.                       |

<Note>
  The `/billing/claims` endpoints are documented on the **Billing** reference
  page. The `/users` endpoints are documented on the **Users** reference page.
  Both pages are available in the sidebar under **API Reference**.
</Note>
